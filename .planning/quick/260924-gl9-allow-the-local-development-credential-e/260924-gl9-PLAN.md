# Quick Task 260924-gl9

Make a newly registered account usable in a plain local `next dev` process by extending the already-approved, server-derived local-only exception through the credential-grant exchange. Vercel Preview, Vercel production, test, and every other deployed execution must retain the existing fail-closed trusted-IP and atomic rate-limit controls.

## Implementation tasks

1. Start with focused regression tests in the existing suites. In `apps/web/__tests__/lib/request-ip.test.ts`, rename coverage for the server-only local-runtime predicate to reflect both registration and credentials while retaining the exact allowlist: only `NODE_ENV=development` with both `VERCEL` and `VERCEL_ENV` empty/absent passes. In `apps/web/__tests__/api/register.test.ts`, update the mock/import only for that renamed predicate and retain the previous local registration and Vercel Preview/production failure-closure assertions. In `apps/web/__tests__/api/auth-controls.test.ts`, isolate and restore `process.env` per test; add a valid local-development credential exchange with no Vercel header and spoofed `forwarded`/`x-forwarded-for` headers that returns a grant while invoking neither trusted-IP parsing nor atomic reservation. Add Vercel Preview and production cases that prove unavailable trusted IP and unavailable reservation still return 503 before credential verification or grant issuance. Keep the existing bounded-payload, retry-aware 429, and one-use grant tests.

2. In `apps/web/lib/server/request-ip.ts`, rename the existing registration-specific runtime predicate to an authentication-wide server-only predicate without broadening its condition. It must continue to accept an injectable environment record for unit tests, evaluate only runtime environment values, and never inspect request headers. Update `apps/web/app/api/register/route.ts` to consume the renamed predicate with no behavior change to its validated local branch or its deployed Vercel reservation ordering.

3. In `apps/web/app/api/auth/credentials/route.ts`, evaluate the same server-derived predicate only after exact credential-body validation. For the sole allowed plain local-development branch, bypass the unavailable Vercel IP and Upstash reservation dependencies, ignore every forwarded header, verify the submitted credentials normally, and issue the existing short-lived one-use grant with a fixed server-owned local-development marker rather than request-derived IP data. For every non-local execution, retain the exact existing order: trusted `x-vercel-forwarded-for` parsing, atomic sign-in reservation, 503 on unavailable dependencies, 429 with the existing retry/reset contract on denial, asynchronous credential verification, then grant issuance. Do not change `AuthForm`, NextAuth authorization, grant single-use behavior, or the generic rate-limit service.

## Threat mitigations

| Threat | Mitigation and required proof |
| --- | --- |
| A browser forges forwarded headers to opt into the local bypass | The predicate reads only server runtime environment; the local credentials test sends spoofed forwarding headers and proves the trusted-IP parser is not called. |
| Preview or production deployment inherits local authentication bypass | The predicate remains exact development mode plus no Vercel markers; direct unit tests plus Preview/production credential-route tests prove 503 fail closure before verification or a grant. |
| Missing Upstash limiter permits deployed sign-in attempts | Only a plain local process bypasses reservation. Every other environment retains an atomic sign-in reservation before credential lookup, with unavailable limiter returning 503. |
| Local development weakens credential grant semantics | The route still verifies stored credentials and issues the existing opaque, short-lived, single-use grant. The fixed local marker is server-owned and no request header is accepted as identity evidence. |
| Registration flow regresses while broadening the helper name | The existing registration route and its tests keep the same branch, payload validation, server-derived role, reservation ordering, and Vercel failure-closure coverage. |

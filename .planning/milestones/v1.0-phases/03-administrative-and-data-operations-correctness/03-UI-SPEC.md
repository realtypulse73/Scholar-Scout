# Phase 03 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

## Design System

| Property | Value |
|----------|-------|
| Tool | Existing Scholar Scout Tailwind design system; do not initialize shadcn |
| Preset | Not applicable |
| Component library | Repository-native `Button`, `Card`, `Input`, and `Badge` primitives |
| Icon library | None; use text labels and status badges, not a new icon dependency |
| Font | Geist Sans; Geist Mono only for package contents, digests, IDs, and typed confirmation values |

Extend the existing `ProgrammeAdminManager` data-operations surface rather than creating a second admin namespace. Reuse the repository primitives and the `brand`, `ink`, `success`, `warning`, and `danger` Tailwind scales. New reusable controls must be added to `apps/web/components/ui/` only when at least two admin states need the same behavior.

## Spacing Scale

Declared values (must be multiples of 4):

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Badge internals and tightly related label/value pairs |
| sm | 8px | Inline control gaps and compact metric spacing |
| md | 16px | Default field, alert, and card-content spacing |
| lg | 24px | Card padding and separation between operation groups |
| xl | 32px | Major panel gaps on desktop |
| 2xl | 48px | Separation between admin page sections |
| 3xl | 64px | Page-level top and bottom breathing room |

Exceptions: interactive targets use the established 44px `min-h-touch` token; compact secondary actions may use 40px minimum height. Do not reduce either target for dense backup rows.

## Typography

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body | 14px | 400 | 1.5 |
| Label | 12px | 600 | 1.5 |
| Heading | 20px | 600 | 1.2 |
| Display | 28px | 600 | 1.2 |

Use only 400 and 600 in Phase 3 additions. Use sentence case for headings and controls. Render backup IDs, incident IDs, content digests, schema versions, and the typed confirmation phrase in Geist Mono at 12px or 14px; allow breaking at safe boundaries and never truncate the only support identifier.

## Color

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#ffffff` (`white`) | Page background, primary panels, inputs, tables |
| Secondary (30%) | `#f8fafc` (`ink-50`) | Nested cards, read-only summaries, metric tiles, locked controls |
| Accent (10%) | `#2563eb` (`brand-600`) | Refresh/Retry, Validate package, Preview impact, focus rings, active capability state |
| Destructive | `#dc2626` (`danger-600`) | Final Apply restore/import actions and their immediate destructive warning only |

Accent reserved for: primary non-destructive actions, keyboard focus, selected operation state, and the border/badge of a read-only server plan. Success (`#059669`) communicates a verified healthy or completed state; warning (`#d97706`) communicates review-required or expiring state; neither substitutes for text. Destructive red must not color preview or validation actions because those are non-mutating.

## Copywriting Contract

| Element | Copy |
|---------|------|
| Primary CTA | `Refresh data operations` on the capability overview; `Validate import package` within import |
| Empty state heading | `No recovery backups yet` |
| Empty state body | `Recovery backups appear here after a confirmed restore or import. No action is needed.` |
| Error state | `Data operations are unavailable. No data was changed. Retry a fresh storage check. Incident ID: {incidentId}` |
| Destructive confirmation | `Apply restore`: `This replaces the current Scholar Scout data as one operation. A recovery backup will be created first. Enter a reason and type RESTORE SCHOLARSCOUT DATA to continue.` |

Additional fixed labels and messages:

- Capability unavailable: `{operationName} is unavailable. {safeReason}` followed by `Retry` only when the server marks the capability retryable.
- Loading: `Checking data operations…`; retain the last-known operation card during an explicit refresh and mark it `Refreshing`.
- Healthy status: `Storage verified`; degraded or failed reads must never display zero counts or an editable empty substitute.
- Preview CTA: `Preview restore impact`; preview badge: `Read-only plan`; preview expiry: `This plan expires at {time}. Preview again if it expires.`
- Validation success: `Import package validated. Review the impact before applying it.` Validation must not say “restored,” “imported,” or otherwise imply a write.
- Version mismatch: `The stored data changed after this preview. No data was changed. Preview the operation again.`
- Success: `Restore completed. Recovery backup {backupId} was created.` Include timestamp and audit/operation ID when available.
- Failure: `{operationName} could not be completed. No partial changes were applied. Incident ID: {incidentId}` Never expose provider details or package contents.

Destructive actions in scope are applying a backup restore and applying a validated import. Both use the same server-plan flow: read-only impact preview, non-empty reason, exact typed phrase, enabled destructive button only while the bound server plan is valid, then an all-or-nothing result. Do not use a browser-only confirm dialog as the safeguard.

## Interaction Contract

### Capability overview

- Treat the storage-health and capability summary as the primary visual anchor on initial load. When a recovery operation is active, its progressive preview/confirmation panel becomes the secondary focal point without displacing the health summary.
- On initial entry, request the authorized server capability contract once. Render only operations reported as available and allowed; the client must not keep or infer its own endpoint inventory.
- Present storage health, adapter label, last verified time, and operation cards in one `Card`. Each visible operation card names the operation, state, safe reason when applicable, and available action.
- A staff-triggered `Refresh data operations` or operation-level `Retry` performs a fresh read and validation. There is no background polling.
- If refresh fails after a prior success, retain last-known counts as read-only, label them `Last verified {time}`, show the inline unavailable alert, and disable every mutation. Never replace counts with zeros.
- The locked state uses a visible alert with `role="alert"`, the safe category, incident ID, and Retry. Disabled controls remain discoverable with adjacent explanatory text; do not rely on disabled-button tooltips.

### Backup history and retention

- Show newest first. Each row contains creation time, non-sensitive actor label, reason category, schema version, shortened visual digest with full selectable value, record-count summary, and retention state.
- Show at most 10 retained backups under normal policy. Mark incident-held backups `Retention hold`; do not present a delete action in Phase 3.
- Use a responsive stacked card list below 640px. From 640px upward, counts may use a five-column grid. Long reasons and IDs wrap without horizontal page overflow.
- The zero-backup state uses the copywriting rows above. A failed backup-list read is an unavailable state, not the empty state.

### Restore and import plan

- A preview shows category counts only in four columns: Data, Current, After restore, Change. It must never render student rows, content samples, email addresses, or snapshot contents.
- On narrow screens the comparison table scrolls within its bordered region; the page itself must not horizontally scroll. Preserve row headers and a visible `Impact preview` heading outside the scroll region.
- Associate the plan visually with its exact backup/package ID, digest, schema version, created time, current-data version, and expiry. Render sensitive-free identifiers in mono text.
- Keep preview and confirmation in one progressive flow. The reason and typed-confirmation fields do not appear until a valid preview exists. Expiry or version conflict disables Apply and returns focus to `Preview restore impact`.
- Import entry accepts a file or bounded text package according to the implemented contract. Display filename only as a convenience and explicitly label server validation as authoritative. During validation, disable duplicate submission and expose progress text.
- Validation produces a staged server plan and does not modify data. Applying that plan uses the identical preview, reason, typed confirmation, version check, recovery-backup, and result pattern as backup restore.

### Feedback and accessibility

- Move keyboard focus to the new preview heading after a successful preview, to the inline alert after a failure, and to the result heading after Apply. Use a polite live region for loading and success; use an assertive alert for unavailable/error states.
- All inputs have persistent visible labels. Connect reason, typed confirmation, and package errors with `aria-describedby`; set `aria-invalid` only after validation.
- Status uses text plus badge color. Retry and Apply labels name the operation; do not use ambiguous `Continue`, `Confirm`, or icon-only actions.
- Preserve entered reason after retryable failures. Clear the typed confirmation whenever the plan expires, the source changes, the stored-data version changes, or a new preview is requested.
- Prevent duplicate mutations while Apply is pending. The pending button label is `Applying restore…`; on completion, announce whether the operation was complete or unchanged.

| Category | Element(s) | Status | Resolution / Reason |
|----------|------------|--------|---------------------|
| loading | Capability overview | ✅ covered | Initial load shows `Checking data operations…`; explicit refresh retains last-known read-only content and labels it `Refreshing` |
| error | Storage and capability reads | ✅ covered | Explicit unavailable alert contains safe category, incident ID, and Retry; all mutations remain disabled |
| empty | Storage data | ✅ covered | A valid zero-count dataset is shown only after a verified successful read and is never synthesized from failure |
| empty | Backup history | ✅ covered | Verified empty collection renders the documented `No recovery backups yet` copy |

| zero-one-many | Backup history | ✅ covered | Zero uses the empty state; one and many use the same newest-first card list capped by server retention policy |
| loading | Preview and validation | ✅ covered | Submission is disabled, progress is announced, and no mutation wording appears while awaiting the server plan |
| error | Preview expired or version changed | ✅ covered | Apply is disabled, typed confirmation is cleared, and focus returns to Preview with explicit re-preview copy |
| partial | Failed restore/import | ✅ covered | Result says no partial changes were applied and includes the safe incident ID; stale success is never retained |
| overflow | Impact comparison | ✅ covered | Table scrolls inside its region on narrow viewports; page does not horizontally scroll |

01

Know what GSD is solving

GSD is most useful when a task has enough uncertainty, scope, or risk that a one-shot prompt would leave important work unspoken.

Context rot

Long agent sessions accumulate irrelevant detail. GSD keeps durable artifacts in the project, then gives heavy research, planning, and execution work fresh contexts.

Invisible decisions

Trade-offs written only in chat vanish at handoff time. GSD turns them into planning context that an executor can follow.

The effective mindset

Do not ask, “Can the agent code this?” Ask, “What must be true for this change to be safe, complete, and easy to resume?”

Rule of thumb: use the smallest workflow that still makes the risk visible. A typo needs momentum; a new API, a bug with an unknown cause, or a multi-file feature needs evidence.

Follow the phase loop

The normal workflow is deliberate on purpose. Each stage creates an artifact that protects the next one from assumptions.

Start a new project

$gsd-new-project captures product context and turns it into requirements and a roadmap. For an existing codebase, begin with $gsd-onboard.

Resume intelligently

When you are unsure where work stopped, use $gsd-progress for the status and next step, or $gsd:next when you want an interactive state-aware router.

03

Choose the smallest honest command

Command choice is where most GSD leverage lives. Use the task’s uncertainty—not its apparent size—to decide how much process you need.

SituationUse thisDepth
One obvious, reversible change$gsd-fast "fix the README typo"Inline
Ad-hoc change with multiple steps or a testable outcome$gsd-quick --validate "add CSV export"Quick task
Cause unknown; investigate before changing code$gsd-debug --diagnose "intermittent 500 on checkout"Evidence-first
A roadmap phase or new product capability$gsd-discuss-phase → $gsd-plan-phase → $gsd-execute-phasePhase
Unsure what comes next in an existing project$gsd-progress or $gsd:nextNavigate
Do not use $gsd-fast as a shortcut around uncertainty. It is for trivial, well-understood changes. Move up to $gsd-quick as soon as research, multi-step planning, or verification matters.
04

Practice command judgment

Choose the best first command for each situation. Getting a “wrong” answer is useful: read the explanation and try again.

Scenario A — production error

A customer reports sporadic 500 responses after a billing-service timeout. You do not yet know whether the cause is retry behavior, a data edge case, or a deployment issue.

Scenario B — bounded feature

You need an admin CSV export. The outcome is clear, but it touches authorization, API output, UI wiring, and tests. You want a plan and verification without turning it into a whole roadmap phase.

Scenario C — planned capability

Your roadmap has a phase for role-based access. It has important decisions around migration, behavior for existing accounts, and release safety.

05

Give the workflow a useful brief

Good GSD inputs make success, constraints, and evidence explicit. Name the outcome—not merely the implementation you first imagined.

Weak request

$ $gsd-quick "improve auth"

It hides the actor, risk, desired behavior, constraints, and proof. The agent must invent them.

Strong request

$ $gsd-quick --discuss --validate "Require sign-in for account exports; preserve staff access; return a clear 401/403 response; add route tests."

It gives a goal, a constraint, expected behavior, and a verification direction. --discuss is appropriate because authorization policy may contain a real decision.

1. Outcome

Who should be able to do what when the work is finished?

2. Boundaries

What must remain true? Mention compatibility, security, data, rollout, or design constraints.

3. Evidence

How will you know it works? Name a test, observable behavior, report, or human UAT check.

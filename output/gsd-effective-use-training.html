01

Know what GSD is solving

GSD is most useful when a task has enough uncertainty, scope, or risk that a one-shot prompt would leave important work unspoken.

Context rot

Long agent sessions accumulate irrelevant detail. GSD keeps durable artifacts in the project, then gives heavy research, planning, and execution work fresh contexts.

Invisible decisions

Trade-offs written only in chat vanish at handoff time. GSD turns them into planning context that an executor can follow.

The effective mindset

Do not ask, “Can the agent code this?” Ask, “What must be true for this change to be safe, complete, and easy to resume?”

Rule of thumb: use the smallest workflow that still makes the risk visible. A typo needs momentum; a new API, a bug with an unknown cause, or a multi-file feature needs evidence.
02

Follow the phase loop

The normal workflow is deliberate on purpose. Each stage creates an artifact that protects the next one from assumptions.

Discuss

Resolve gray areas and lock meaningful product or technical decisions before they become code.

CONTEXT.md$gsd-discuss-phase 2
Plan

Research, slice the work, add verification, and check that the plan can actually achieve the phase goal.

PLAN.md$gsd-plan-phase 2
Execute

Use focused executors and small commits. The plan, not chat memory, provides the working brief.

SUMMARY.md$gsd-execute-phase 2
Verify

Test the promised outcomes and use UAT for what needs human judgment. Fix gaps before declaring victory.

UAT.md$gsd-verify-work 2
Ship

Prepare the reviewable change, preserve evidence, and move the milestone forward without losing the learning.

PR + STATE.md$gsd-ship 2 --draft

Start a new project

$gsd-new-project captures product context and turns it into requirements and a roadmap. For an existing codebase, begin with $gsd-onboard.

Resume intelligently

When you are unsure where work stopped, use $gsd-progress for the status and next step, or $gsd:next when you want an interactive state-aware router.

03

Curriculum: learn before you test

Read these six lessons in order. Every assessment question below is grounded in one of these concepts or commands.

Lesson 1 — Orient yourself

GSD protects against context rot by keeping durable decisions and progress in project artifacts. In Codex, invoke commands with a dollar sign.

  • Use $gsd-new-project for greenfield setup.
  • Use $gsd-onboard for an existing repository.
  • Use $gsd-progress for status and $gsd:next for a state-aware menu.

Lesson 2 — Match workflow depth to risk

Pick the smallest process that makes uncertainty visible.

  • $gsd-fast "..." is for trivial, well-understood, reversible edits.
  • $gsd-quick --validate "..." is for bounded, multi-step work needing a plan and proof.
  • $gsd-debug --diagnose "..." investigates an unknown cause without attempting a fix.

Lesson 3 — Discuss and plan a phase

Use the phase number you are working on. Discussion captures decisions before research or implementation begins.

  • $gsd-discuss-phase 2 creates decision context such as CONTEXT.md.
  • $gsd-plan-phase 2 researches, decomposes, and validates the phase plan.
  • $gsd-plan-phase 2 --research refreshes research; --skip-research is for a familiar domain.

Lesson 4 — Execute, verify, and ship

Execution follows the plan; verification checks the user-visible outcome; shipping prepares the reviewable change.

  • $gsd-execute-phase 2 runs phase plans in dependency-aware waves.
  • $gsd-verify-work 2 runs conversational UAT and records it in UAT.md.
  • $gsd-ship 2 --draft creates a draft PR after required verification passes.

Lesson 5 — Use flags deliberately

Flags are opt-in: a documented flag does nothing unless you type it.

  • --wave 2 runs only execution wave 2; --interactive executes sequentially with checkpoints.
  • --gaps-only targets fix plans created after verification gaps.
  • $gsd-discuss-phase 2 --assumptions surfaces implementation assumptions instead of a normal discussion.

Lesson 6 — Make a good brief

Describe the outcome, the boundaries, and the proof. When you come back, read STATE.md and plan summaries instead of reconstructing history from chat.

  • State who should be able to do what.
  • Name constraints such as security, compatibility, or rollout safety.
  • Ask for tests, observable behavior, or UAT evidence.
04

Choose the smallest honest command

Command choice is where most GSD leverage lives. Use the task’s uncertainty—not its apparent size—to decide how much process you need.

SituationUse thisDepth
One obvious, reversible change$gsd-fast "fix the README typo"Inline
Ad-hoc change with multiple steps or a testable outcome$gsd-quick --validate "add CSV export"Quick task
Cause unknown; investigate before changing code$gsd-debug --diagnose "intermittent 500 on checkout"Evidence-first
A roadmap phase or new product capability$gsd-discuss-phase → $gsd-plan-phase → $gsd-execute-phasePhase
Unsure what comes next in an existing project$gsd-progress or $gsd:nextNavigate
Do not use $gsd-fast as a shortcut around uncertainty. It is for trivial, well-understood changes. Move up to $gsd-quick as soon as research, multi-step planning, or verification matters.

06

Give the workflow a useful brief

Good GSD inputs make success, constraints, and evidence explicit. Name the outcome—not merely the implementation you first imagined.

Weak request

$ $gsd-quick "improve auth"

It hides the actor, risk, desired behavior, constraints, and proof. The agent must invent them.

Strong request

$ $gsd-quick --discuss --validate "Require sign-in for account exports; preserve staff access; return a clear 401/403 response; add route tests."

It gives a goal, a constraint, expected behavior, and a verification direction. --discuss is appropriate because authorization policy may contain a real decision.

1. Outcome

Who should be able to do what when the work is finished?

2. Boundaries

What must remain true? Mention compatibility, security, data, rollout, or design constraints.

3. Evidence

How will you know it works? Name a test, observable behavior, report, or human UAT check.
